Understood as: transpose chord symbols across a PDF, let the user choose file/song/page scope, export a PDF, and add a separate tablet reader with device-local handwriting and optional on-device wink navigation. Melody transposition belongs to cm3 and must not be implied by this feature.

## 1. Recommendation and acceptance

Keep one cm2 worktree and deliver PDF, handwriting, then wink as sequential slices. Use server-side pypdfium2 for bounded rasterization and raster PDF export; display page images in the reader. This avoids adding a second PDF renderer or a browser PDF writer. The output preserves page count, order, physical page sizes, lyrics and notation visually, but is a flattened raster PDF: searchable text, interactive forms and source vectors are not preserved. The owner approves this tradeoff before implementation.

Existing home layout code remains untouched; `/pdf` and `/reader` are directly addressable routes. A home entry point needs a separate rendered proposal and owner approval.

Owner-confirmed addition (2026-10-14): `frontend/next.config.js` belongs to cm2 solely for reader-only camera permissions. cm3 owns the canonical proposed `backend/omr/intent.py` contract; cm2 owns only a `backend/pdf/intent_adapter.py` boundary and `frontend/lib/transpose-intent.*`. Agree the schema in writing before implementation; do not create a competing contract under cm1-owned `backend/chords/`.

The existing global `Permissions-Policy: camera=()` blocks wink. Set the global camera/microphone/geolocation denial first, then a reader-only header allowing `camera=(self)` while microphone/geolocation remain disabled. Next.js uses the last matching value for a duplicate header ([official headers reference](https://nextjs.org/docs/pages/api-reference/config/next-config-js/headers)). A client-side route change does not replace the document's Permissions Policy: entry to and exit from the reader must use full document navigation, not SPA navigation. Test direct entry, `/pdf` -> `/reader`, reader -> non-reader, actual document response headers, permission behavior and track shutdown. Keep camera disabled on every other route. Do not change any hosting console.

The cm3 intent contract must be agreed before PDF controls: `intent=capo` with `capo_fret=0..7`, or `intent=key_change` with `semitones=-11..11`; mutually exclusive fields, invalid combinations -> 422. PDF v2 initially changes chords only and says so. Capo leaves notes and key signatures unchanged. Legacy `/render` remains compatible. cm3 owns a new notes renderer; it does not edit cm2's API or home files.

Tester owns only `tests/pdf/**` and `frontend/**/__tests__/**`. The current `npm test` glob only discovers `frontend/test/*.test.mjs`; cm2-dev must add an explicit command/glob for the new test directory through the coordinated package edit before tests can count. Dev does not edit tester files. Python requirements and frontend package/lock changes occur one feature at a time under the orchestrator.

Do not create cm4: PDF and reader share document identity, page coordinates, progress, i18n and camera configuration. A future split is possible but would require the owner's explicit approval.

### Proposed API and state

- `POST /pdf/jobs`: 202 with unpredictable job ID plus a separate guest job capability. Return the capability once; require it in a header on every job operation, never a query URL. Keep the capability in tab-scoped `sessionStorage` so a full-document reader navigation can recover the job; delete on cancel/expiry and never put it in IndexedDB, URLs or logs.
- `GET /pdf/jobs/{id}`: status, per-page title/key, grouping suggestions, counts, errors, revision. States: queued, analyzing, needs_review, rendering, ready, canceled, failed, expired.
- `PUT /pdf/jobs/{id}/settings`: explicit groups and file/song/page shift map. Precedence: page override > song override > file default; reject overlaps, out-of-range pages and inconsistent intent. Revision increments on edit; stale results cannot overwrite newer settings.
- `POST /pdf/jobs/{id}/renders`: create a result revision without repeating OCR. Unknown title/key requires explicit grouping/key review, not a silent guess. Blank pages retain original raster.
- `GET /pdf/jobs/{id}/pages/{page}` and `/result`: capability + revision required, `Cache-Control: no-store`; result only when every selected page completed. No partial PDF presented as complete.
- `DELETE /pdf/jobs/{id}`: cancel further pages and remove stored source/results. Already-admitted OCR may finish; discard its output, release admission, and do not schedule another page. Cancellation must not falsely claim to terminate a running Python thread.

PDF jobs must not insert all pages into `_detection_cache` (20 entries / 80 M pixels). Use a bounded document store for source bytes, chord metadata and encoded outputs; rasterize only the current page, then release bitmaps. Share the existing OCR admission/executor via an explicit adapter owned by cm2; no hidden second Paddle model or bypass around busy responses. When cm1's custom engine becomes available, consume the same callable contract without importing its implementation.

PDFium is not thread-safe, even across different documents ([official API](https://pypdfium2.readthedocs.io/en/stable/python_api.html#incompatibility-with-threading)). All PDFium calls use one serialized worker process with explicit handle closure; do not call it concurrently from FastAPI request threads. Export by creating a new PDF with page-sized raster image objects; validate encode/decode on rotated and mixed-size pages. No user PDF JavaScript, embedded files or active links are executed/copied.

### Limits and runtime cost

Initial limits: 20 MiB input, 10 pages, 8 M pixels per raster, at most two live decoded pages (16 M pixels), 128 MiB encoded source/result bytes per job, two live jobs globally, one per anonymous session capability. Issue a separate random session token into tab-scoped `sessionStorage`, send it only in a header, and bind at most one live job to it server-side. It is an anonymous capability, not an authenticated person: a client can obtain another session, so the global two-job limit and shared page admission remain the enforceable resource boundary. Job-access capability and session token have separate roles. Neither is logged. Clear expired credentials on the next client action; server TTL remains authoritative even if the tab is closed. Refuse a result above its byte budget. Check dimensions before allocating. Expire inactive jobs after 15 minutes, hard lifetime 30 minutes; delete on explicit cancel, failure or shutdown. No server disk persistence of user PDFs or annotations. Restart loses jobs with a clear re-upload message.

Current 13-24 s/page is a historical observation, not a fresh measurement. Ten pages imply roughly 130-240 s of OCR alone; extra render/raster/queue time is additional. Do not assume cm1 succeeds or use its 2x target as a current speed claim. Target total warm p95 <=300 s for the fixed ten-page reference document; max document execution budget 600 s, no further pages after expiry. A running OCR call may outlive cancellation until it returns; test this explicitly.

On the current [HF CPU Basic](https://huggingface.co/docs/hub/spaces-overview), budget for 2 vCPU / 16 GB RAM. Proposed incremental process-tree peak RSS <=512 MiB over the existing image service, total container <=10 GiB; OOM count 0. Measure Linux x86_64 process-tree RSS and cgroup peak, not macOS or a Python-only allocation counter. Baseline and PDF-load runs each use at least 30 identical image requests in three paired rounds; image p50/p95 slowdown <=5% and new 5xx count 0. Failure blocks shared-host activation.

No server-side ML model is added by PDF parsing. pypdfium2 5.14.0's manylinux x86_64 wheel is approximately 3.8 MB compressed; installed native size/RSS are NOT MEASURED. The face task asset is approximately 3.76 MB, while JS/WASM package size is additional and measured at build time. Camera inference runs on-device at a capped 10-15 FPS in a worker where supported; synchronous inference must not block handwriting. All latency/RSS targets remain **NOT RUN**.

## 3. Reader, handwriting and wink behavior

Reader access requires a touch-capable tablet-sized viewport (proposed width >=768 CSS px and touch capability), with an unsupported-device explanation otherwise. It is a new web route; phone/desktop homes and Apps-in-Toss remain unchanged. Verify iPad split view and orientation; do not infer an iPad from user-agent text alone. A keyboard/button page-turn fallback remains available.

Use Pointer Events, pointer capture, normalized page coordinates and an explicit pen/touch mode. In pen mode, fingers pan/zoom and palm contacts do not draw; touch drawing requires selecting that mode. Store strokes and optional explicitly saved page images in IndexedDB keyed by local document hash + page + rendition revision. A transposition revision cannot silently attach old strokes to changed geometry; require keeping/resetting that annotation layer. Provide local clear-document and clear-all controls. Browser quota failure or eviction must show an honest unsaved/lost-state message; local storage is not a backup or cross-device sync.

Wink: user calibration defines anatomical left/right independently of mirrored preview. Proposed defaults: left = previous, right = next; user can invert. Require one eye closed and the other open for >=200 ms, both eyes reopened before rearming, and >=1,000 ms cooldown. Reject bilateral blinks, multiple faces and uncertain tracking. Suppress turns during drawing and at document boundaries. Camera off and landmark buffers released on route exit, hidden page or explicit disable. No frame, landmark sequence or facial template is stored or transmitted. Self-host pinned WASM/model files; do not use runtime `@latest` CDNs. Network inspection must show no camera-derived upload, telemetry or Sentry replay payload.

The [official Face Landmarker guide](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker/web_js) describes video inference and blendshapes; it does not prove this app works on iPad Safari. Real-device HTTPS checks are a mandatory separate gate. Test current and one prior supported iPadOS major on actual hardware, record exact builds and camera placement. If unavailable, mark NOT RUN and keep wink disabled.

Separate calibration trials from evaluation. A randomized cue log establishes deliberate left/right wink truth independently of the recognizer; an observer checks compliance without recording frames. Run the natural-blink trial during an actual reading task, with independent turn/error counts. Do not tell testers the acceptance threshold while they perform the task. Report incomplete cues, observer disagreement and the unblinded study limitation. Nineteen successes in twenty trials is only the stated small-sample gate, not proof of a population-wide 95% rate.
